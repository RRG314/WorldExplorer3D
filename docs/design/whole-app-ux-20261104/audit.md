# Current UX and system audit

Baseline: the deployed runtime `98c86efee14e`, with release documentation at `5b352b998b38856c84390e6c18763ba6db211511`. This is a new product-design audit. Earlier accepted gameplay, save compatibility and release evidence remain accepted; their procedures were not replayed.

## Coverage and evidence levels

- **Current live observation:** public selector at 1440×960 and 390×844; Activities and an Archaeologist brief; phone Settings; free Space UI and Wayfinder at desktop/phone; Coral Shelf research-vessel entry and its settled deck UI. No career completion, race, purchase, room join, account creation/deletion or publication was performed. The isolated browser's local introductory state is not a player's history.
- **Current source inventory:**172 feature/system entries, all 20 careers,100 capability descriptions,15 quick-play/route references (overlapping);72 UI surfaces cross-referenced to existing files. All referenced paths exist. Source scale:1,374 `app/js` files and258,724 lines. This is feature/architecture coverage and focused owner tracing, not a line-by-line audit of that entire source volume.
- **Retained evidence:** the approved immutable world/Backpack/career/save and domain acceptance identified in the release record; prior Earth, underwater, planetary and platform work where unchanged. Those are not newly observed user sessions or physical-device acceptance.
- **Not newly tested:** uncoached players, retention, actual phone/controller/headset/assistive devices, screen readers, authenticated multiplayer/payment/contribution journeys, every locality/provider, or every science procedure. Source presence does not establish universal usability or conformance.

Raw snapshots and screenshots remain in `output/playwright/whole-app-ux-20261104/`, excluded from Git. This report records observations, design risks and proposed verification separately. No production behavior was changed.

P1 means high-impact understanding/discoverability work; P2 means important efficiency/consistency work. These priorities are design assessments, not measured abandonment rates or security severity.

## What should be kept

Stable experience IDs and adapters, the twenty varied career procedures, exact saved evidence, selected real vehicles/three venues, existing player/room/ship ownership, meaningful save-failure retry, modal and world-focus handling, body landing/truth policies, original photo backup, configurable accessibility, and established render/asset lifetimes. The phone career brief's persistent primary action and explicit browser-local progress explanation are useful existing patterns.

The architecture already has many necessary domain boundaries. The next change should compose their presentation and improve hierarchy. A renderer/framework rewrite or a new unified game database would add risk without solving the observed navigation problems.
