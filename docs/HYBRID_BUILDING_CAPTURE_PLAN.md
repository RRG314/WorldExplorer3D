# Building-specific capture, partial coverage and video

September 7, 2026. Implementation plan; explicitly not a declaration that hybrid publication or video capture is complete. Existing capture/account/storage/worker and building authorities stay in place. No new paid reconstruction until local and toolchain gates are satisfied.

## What failed and what is known

The owner's 21 immutable photos reached the worker. The output displayed one gable wall rather than the full five-unit, two-story complex. The original camera-registration and intermediate mesh files were deleted by the worker, so the exact original loss stage is not recoverable from the stored GLB alone. Facade scope was not a Meshroom crop instruction. Upload normalization stripped camera metadata and the worker initialized one camera group with default field of view; this is a weakness, not a proven sole cause.

A local CPU audit of those actual 21 images used OpenCV 4.11 SIFT, reciprocal ratio matching, and fundamental-matrix RANSAC. At 15, 25 and 40 minimum inliers, the diagnostic found respectively 5, 6 and 9 disconnected groups (also requiring 40% inlier ratio and 5% image-area span). Several within-group pairs had hundreds of inliers. This supports insufficient linking views as a likely contributor; it is not an exact replay of AliceVision, proof that every link is geometrically correct, or proof that cleanup was uninvolved. Photos are not generally featureless. Do not discard them or ask the owner to retake everything.

## Product rule

One real mapped building has one evolving presentation record. Observed contributions apply only to their registered surface regions. Unobserved regions keep their procedural presentation. Better future evidence can supersede a region without destroying other regions or history. An observed wall must never become a shared material used by unrelated buildings.

## Testable private hybrid preview — September 7 checkpoint

The existing capture panel now opens a photo/footprint editor for saved exterior captures with mapped footprints. It reuses owner-authenticated original access (pinned to validated storage generations), the current 3D viewer, and the existing mapped-roof generator. Four explicitly selected photo corners are rectified with a planar homography and placed on a selected wall region. Other surfaces remain procedural. Users can add, adjust, remove and undo patches, change provisional wall/roof dimensions, orbit/zoom, and save private revisions to the same capture/account. The API checks the owner, footprint signature, input manifest, geometry bounds and expected revision. It preserves the previous ten private revisions; it never changes the original reconstruction, canonical footprint, public representation, door or collision state.

The actual owner's saved front-wall photo was decoded and projected locally onto their saved footprint. Manual correspondence is an example requiring owner review, not solved camera registration or a complete reconstruction. The first visual test exposed a numeric-field blur bug that changed corner coordinates; this was fixed and an exact-coordinate assertion added. Desktop and 390px preview, save/reopen, remove/undo and abort disposal passed. HTTP tests execute the real handler with explicit infrastructure doubles. Physical phone performance and live account save must be distinguished from these local checks.

Still not implemented: automatic whole-building photo registration, photo-supported roof patches, arbitrary polygon masks/occluder removal, cross-capture surface aggregation, global manifest migration, public hybrid publication and in-world partial-patch attachment. This checkpoint is a private testable editor, not completion of the entire roadmap. The retained private revision history is not yet a user-facing history browser. Unknown roof/height inputs remain visibly provisional.

## Implementation sequence and gates

1. **Evidence first.** Preserve private per-attempt solved cameras, matching statistics, component summaries and pre/post-optimizer geometry with bounded retention, including failed attempts. The existing new bounded registration summary is only the first part. Split camera registration from dense meshing only after executing the actual Meshroom CLI/resume behavior. Flag disconnected inputs before dense processing; keep them available for augmentation.
2. **Building details.** Optional floors, units, roof shape, measured height and labelled reference dimensions live on the capture as `user-reported-unverified`. Unknown stays unknown. Existing mapped height/footprint provenance is never silently overwritten. Corrections need evidence review; photos and measurements must use a consistent reference (door leaf versus brick-to-brick opening). Current local form/server normalization implements this intake, not automatic calibration.
3. **Surface registration.** Show the selected building footprint and numbered wall segments, roof outline and existing contributions. Users select the surface, outline the visible wall in the photo, and mark matching corners/reference points. Use a planar homography only for sufficiently planar walls; balconies, curves, depth discontinuities and roof planes need separate patches or registered meshes. Show reprojection error, scale and a mapped-building overlay. Do not infer unavailable GPS/camera calibration. Touch handles must be large, zoomable and undoable, with keyboard controls on desktop.
4. **Hybrid private preview.** Start with a photo-derived, rectified wall patch. This can improve appearance without a GPU reconstruction. Render only its reviewed polygon on the target wall, with a coverage mask—not a full rectangular photo containing sky, neighbors or cars. Keep procedural walls/roof outside that polygon. Preserve canonical geometry, collision, doors, interior identity, roads and terrain. A 3D scan is an optional later representation of the same surface, not another building authority.
5. **Versioned publication.** Extend the existing moderated representation authority with immutable surface contributions and one revision-checked manifest per canonical entity. A surface contribution records capture/input generations, provider-qualified building identity, footprint revision/signature, surface definition, observed mask, alignment, evidence class, reviewer, rights and derivative asset. Store supersession/withdrawal references rather than overwriting originals. Compare-and-swap on the manifest revision prevents a stale review deleting newer work. Reviewed wall A and wall B must coexist; replacing A must retain B. Competing observations of A require explicit resolution, not last-upload-wins.
6. **Runtime integration.** Extend `reality-capture/runtime.js` through its existing refresh/load/dispose lifecycle. Do not call whole-building suppression for partial patches. Match provider/entity and footprint revision before attachment; stale/mismatched patches fall back visibly in review and to procedural at runtime. Spatial launch origin must not divide one OSM entity into several histories: audit existing origin-derived `worldId` use and migrate capture identity deliberately without altering unrelated saves. Whole-building replacement remains a separately reviewed complete representation. Bound patch count, texture resolution, decoded memory and near-distance loading; do not clone full photo atlases across buildings.
7. **Incremental capture.** Start a new contribution against the existing manifest revision; append new immutable inputs under the same canonical building, never modify already validated generations. Show which surfaces are observed, procedural, outdated or conflicted. Let users add a corner-connection clip or sharper wall photographs rather than restart the whole complex. Invalid registration must not delete earlier good evidence. Keep roof/height discrepancies explicit.
8. **Owner acceptance.** Use the actual complex for a before/after view. Verify one photographed wall with other sides procedural, two sides retained after another contribution, a neighboring building unaffected, correct footprint alignment from different Earth origins, reload/second-account consistency, withdrawal/rollback, and preserved entrance/collision. Test desktop and physical phone before considering broader publication.

## Video is another input, not another reconstruction system

Offer short guided clips and existing-video import, alongside still photos. Reuse the camera lifecycle and account handoff. In-app recording should request no audio; imported audio must never be sent for reconstruction. Explain codec/device support and keep still-photo fallback available. On-device decode capability must be tested; do not promise every HEVC/MOV/WebM variant works on every browser.

Select sharp, sufficiently changed keyframes while retaining links around corners and between upper/lower passes. Combine blur, exposure, near-duplicate and matching evidence; equally spaced frame extraction alone is not acceptance. Show extracted frames, excluded intervals and coverage gaps before upload. A continuous blurry or stationary video is not extra evidence. A long complex may need multiple short clips, still close-ups and explicit surface associations. Walking past a wall is useful; simply rotating the phone in one spot provides limited depth evidence.

Keep source clip identity, frame timestamps and any allowed calibration metadata tied to immutable derived images. Reuse current image validation, manifests, private storage, queue and diagnostics. Do not bypass the current image/byte budgets by accepting a video; develop budgeted incremental capture instead. Prefer local frame selection to uploading large redundant videos. If a server decoder is required, sandbox it, bound bytes/duration/resolution/CPU, validate decoded media, strip audio/location metadata and report cost before processing. Raw videos need explicit private retention/deletion rules, not public URLs.

Test cancellation/backgrounding, unsupported codecs, rotated video, oversized/damaged clips, no usable frames, repeated frames, slow devices, account changes, resumable upload, and frame timestamp provenance. Use actual recorded fixtures with executed decoders, not only mock File objects.

### Local implementation checkpoint

The form now offers a native record/choose-video input, limited to 90 seconds and 150 MB. The browser decodes supported video locally, samples frames, filters near-duplicates, and sends retained JPEGs through the existing normalization and IndexedDB photo store. Neither source video nor audio is uploaded. Frames remain subject to the existing 48-photo capture budget. Timestamps are retained in the local draft only; cloud source-clip/frame provenance remains to be implemented.

A real encoded MP4 passed decoding, frame extraction, local storage and reload in desktop Chrome with a mobile-sized UI. Pre-cancelled import and invalid media rejection passed. Auth/storage transport in this UI test is doubled; it does not establish phone codec support or reconstruction quality. Physical iPhone/Android testing, rotation/backgrounding coverage, advanced sharpness/overlap keyframe selection and complete hybrid surface registration/publication remain unfinished. These changes are local, not deployed. No new GPU reconstruction was launched.

## Existing authority changes, not parallel replacements

- Capture form/local draft/server record: user-reported building details and input provenance.
- Existing worker/broker: registration checkpoints and quality diagnostics; no second uploader or reconstruction queue.
- Existing representation collection/moderation: surface manifests, revision history, authorizations and withdrawal.
- Existing building presentation: registered per-building surface patches, procedural fallback and bounded lifecycle.
- Existing access authority: private originals/interiors remain private. Public exterior never grants interior access.

Unsupported for this first hybrid milestone: synthesized hidden details presented as real, automatic changes to mapped property geometry, automatic full-room collision from photos, global texture replacement, outdoor environment reconstruction, or publication based solely on photo counts.
