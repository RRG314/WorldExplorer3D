<h1>A world that looks like<br>the place you chose.</h1>
<div class="note"><strong>Local implementation update:</strong> numeric land-cover delivery, regional ground materials, curated vegetation, trunk collisions, wetland groundcover and detailed-to-regional terrain edge stitching are now implemented. The original research below describes the starting baseline, not the current feature inventory. Production has not been changed. <a href="implementation-status.md">Implementation and verification status</a> · <a href="EXECUTION_PLAN.md">Step-by-step acceptance plan</a>.</div>
<p class="meta">September 8, 2026 • Prepared for Steven • Current working branch: steven/building-exteriors-local • Environment recommendations, not implemented features.</p>
<p class="lead">Keep the terrain foundation. Replace the weak translation from geographic evidence into ground materials and ecosystems.</p>
<p>You already have elevation providers, mapped land use, WorldCover integration, several ground textures, terrain blending, instanced trees, and nearby collision queries. The unfinished connections between these pieces explain much of the repetitive grass and artificial forests. Buying better trees alone will not solve it.</p>
<div class="note"><strong>Scope:</strong> global Earth ground appearance, vegetation, elevation compatibility, performance, and asset selection. Preserve buildings, roads, bridges, tunnels, cameras, property identities, and the always-drivable BMW. No terrain or vegetation runtime changes were made during this research. Analytics is a separate implementation in the same working branch.</div>

<h2>How games normally solve this</h2>
<p>Separate the large landscape shape from the ground material and the objects growing on it. Materials use several layers and blend weights; foliage uses different populations, spacing and competition rules. Distance-based representations and bounded batches control cost. These are established techniques that can be used in Three.js without migrating engines. <a href="https://dev.epicgames.com/documentation/en-us/unreal-engine/landscape-materials-in-unreal-engine">Epic landscape materials</a> · <a href="https://dev.epicgames.com/documentation/en-us/unreal-engine/procedural-foliage-tool-in-unreal-engine">Epic procedural foliage</a> · <a href="https://threejs.org/docs/pages/InstancedMesh.html">Three.js instancing</a> · <a href="https://threejs.org/docs/pages/LOD.html">Three.js LOD</a></p>
<div class="flow">Accepted elevation + mapped features + numeric land cover + climate context<br>↓<br>One versioned environmental profile per geographic cell<br>↓<br>Ground material weights • vegetation populations • nearby trunk obstacles</div>
<p>The existing terrain renderer, vegetation authority and physics authority remain the consumers. Do not create a second terrain surface, an independent biome height sampler, or a separate forest database.</p>

<h2>The data to use—and its limits</h2>
<ul>
<li><strong>Land cover:</strong> use ESA WorldCover’s numeric classes, keeping all eleven and explicit unknown values. Its 2021 product is approximately 10 m resolution, CC BY 4.0, with reported overall accuracy of 76.7%. It identifies cover, not individual trees or exact present-day conditions. Read source COGs in a preprocessing/service layer and deliver compact cached tiles to browsers; do not download the global dataset per player. <a href="https://esa-worldcover.org/en/data-access">ESA source and terms</a></li>
<li><strong>Climate:</strong> a historical Köppen–Geiger layer can distinguish broad climate context. The publisher offers approximately 1 km maps under CC BY 4.0. Use a documented historical period, not future projections, for the normal world. Climate narrows plausible vegetation; it does not prove species or a tree at a particular coordinate. <a href="https://www.gloh2o.org/koppen/">GloH2O maps, periods and license</a></li>
<li><strong>Elevation:</strong> retain the provider registry and accepted-ground rules. Copernicus DEM is a surface model that includes vegetation and buildings; replacing ground with it blindly can double-count canopy or roof height. Regional bare-earth data can improve terrain where available, after datum normalization. <a href="https://dataspace.copernicus.eu/explore-data/data-collections/copernicus-contributing-missions/collections-description/COP-DEM">Copernicus DEM</a> · <a href="https://www.usgs.gov/3d-elevation-program/about-3dep-products-services">USGS 3DEP</a></li>
<li><strong>Licensing trap:</strong> FABDEM removes forest/building bias but its published license is noncommercial/share-alike. Do not silently adopt it as an unrestricted global baseline for this app. <a href="https://research-information.bris.ac.uk/en/datasets/fabdem-v1-2/">University of Bristol FABDEM</a></li>
<li><strong>Mapped detail:</strong> use existing coast, water, land-use, road and building evidence for local constraints. A park boundary describes designation, not vegetation. Do not interpret every national park as forest or every coast as a sandy beach.</li>
</ul>
<p><strong>Data contract:</strong> cell ID, geographic bounds and coordinate system, source class, nodata mask, source/version/year, provenance, accepted ground revision, climate period, and generator version. Preserve observed classes separately from procedural choices and visual blend weights. Categoricals use nearest-neighbor sampling; visual transitions can be softened afterward.</p>

<h2>Ground that changes appropriately</h2>
<p>Extend the current shared near/far material code. Select a small regional palette: sand, rock, soil, leaf litter, moss/low vegetation, snow/ice, or wet ground as supported. Blend color, normal and roughness consistently. Use meter-based texture scale and world-aligned projection on steep rock faces; derive coordinates from stable geographic anchors so floating-origin shifts do not make textures slide. Blend transitions using slope, mapped boundaries, cover and restrained detail noise—not latitude alone. <a href="https://dev.epicgames.com/documentation/en-us/unreal-engine/texturing-material-functions-in-unreal-engine">World-aligned texturing and material transitions</a></p>
<p>Do not displace the visible terrain independently from the collision ground. Preserve the existing road, bridge, tunnel and water masks. Beaches require shore evidence and local slope/cover; tundra needs low plants, moss and exposed ground rather than miniature temperate trees. Deserts can be naturally bare: the goal is no unexplained default grass, not an object in every square meter.</p>

<h2>Forests you can enter</h2>
<p>Use stable geographic vegetation cells, not terrain vertices or array order. Within each cell, generate varied clusters with minimum spacing: canopy trees, emergent trees where appropriate, saplings, understory, ground cover, and occasional deadwood. Orchards may legitimately have rows; natural forest should not. Recheck every final placement against the actual cover, slope, roads, buildings and water. Sample each tree’s own ground height.</p>
<p>Render by cell × species × detail level. Nearby trees use useful silhouettes and trunks; middle-distance trees use simpler meshes; distant forests use cheap canopy/impostor representations. Correct bounds enable culling. Use hysteresis so crossing a distance threshold does not cause flicker. Do not instantiate a heavyweight scene object for every leaf or a full collision mesh for every tree. <a href="https://threejs.org/docs/pages/InstancedMesh.html">Instanced bounds</a> · <a href="https://threejs.org/docs/pages/LOD.html">Distance levels</a></p>
<p><strong>Collision:</strong> add nearby trunk cylinders/capsules to an indexed obstacle query used by the existing movement solver. Use swept tests for a fast car, not only endpoint overlap. Leaves normally remain non-solid. Visual LOD must not make a nearby trunk suddenly non-solid, and collision must not create invisible distant walls. Keep vehicle response compatible with the free BMW always remaining usable.</p>

<p>Prefer a small consistent library with matching lighting, scale, foliage treatment and material response. Asset inspection, texture compression, mobile memory limits, LOD creation and trunk proxy dimensions are part of integration—not optional cleanup afterward.</p>

<h2>Implementation order and acceptance</h2>
<ol>
<li><strong>Record the baseline.</strong> Freeze exact coordinates, provider evidence, camera route, weather/time and quality tier for the comparison set. Measure loading, frame time, texture memory and draw calls. Keep existing bridge/tunnel cases in the regression set.</li>
<li><strong>Repair environmental evidence.</strong> Replace RGB inference behind the existing land-cover provider contract; keep old input only as explicitly lower-confidence fallback during migration. Add bounded recovery for transient failures. Keep numeric classes separate from the material palette. Validate tile borders, antimeridian behavior, coverage limits and nodata.</li>
<li><strong>Complete ground materials.</strong> Add stable per-cell climate/cover/elevation context and full material blending. Prove near/far agreement and no changes to driveable terrain heights before changing vegetation.</li>
<li><strong>Replace tree generation and rendering rules.</strong> Correct accepted-placement caps and unchecked offsets; move identity to world cells; select vetted regional assets; build bounded instance batches and detail levels. Remove the superseded filler route once the replacement passes.</li>
<li><strong>Connect tree interaction.</strong> Share accepted placements with indexed, nearby collision proxies. Check walking, car impacts, reverse/recovery, slopes, high speed, and transitions across loaded cells.</li>
<li><strong>Accept by region and device.</strong> Desktop and Android/mobile quality tiers must preserve geography while reducing visual detail. Set final budgets from baseline measurements, not an arbitrary global tree limit. No production acceptance from screenshots alone or source-structure tests alone.</li>
</ol>

<p>At each site test fresh load, cached load, provider failure then recovery, movement across tile boundaries, high-speed travel, phone viewport and reduced-detail mode. Compare the same code candidate on both devices. Include reload determinism and clean unload/disposal; a full jungle is not successful if it makes the rest of the world stop loading.</p>

<h2>Decision</h2>
<p><strong>Proceed with an environmental-data and rendering integration, not a terrain rewrite.</strong> The source audit and primary documentation are sufficient to choose this direction. Remaining uncertainties are actual device budgets, site-level data accuracy, and imported-asset suitability; those require implementation measurements, not more broad searching. A geographically grounded procedural forest can look convincing without pretending every tree is a surveyed real tree.</p>
<p class="meta">Research method: current-code inspection; parallel data/rendering and vegetation/asset lanes; primary-source follow-up for the highest-impact claims; targeted licensing check for climate data. No datasets downloaded, no assets purchased, no new cloud processing, no production changes. Broad research stopped once the architectural decision had support; asset and device acceptance remain explicit gates.</p>
