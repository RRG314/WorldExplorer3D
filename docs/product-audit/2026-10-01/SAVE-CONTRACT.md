## Repair completed in this slice

A preference writer could fetch a profile, await other work, then save that stale profile after a discovery transaction had awarded progress. It would overwrite the new progress even though the discovery's event/claim remained saved, preventing a replay from recovering the lost reward. All discovery/companion preference writers now use synchronous transactional profile updaters. Independent tutorial entries merge against current state; companion encounter writes merge by identity and timestamp against the current stored encounters. Tool-save failures are caught instead of becoming unhandled promise rejections.

Validation: 1,616 registered component tests passed, no failed/skipped/TODO. Following the final encounter merge, focused save/starter/character checks and source verification passed. Real browser IndexedDB test used two tabs with simultaneous duplicate claims and preference writes: 20 records, 20 tutorial entries, selected tool and rewards survived reload. Backup import and claim replay did not add rewards. Legacy character migration retained its backup and reopening did not repeat migration. No page exceptions. Prescribed-client storage fixture and actual-source Space regression passed; screenshots inspected.

## October 2 continuation — receipt recovery implemented

- IndexedDB schema 4 adds an account-owned receipt outbox. A new signed-in collected item and its pending receipt commit in the same discovery transaction. Guest items and restored server items are not retroactively enqueued. Existing data stores and migration backups are preserved.
- Runtime startup, reconnect and a bounded 30-second check retry due entries (25 per batch). Transient/ambiguous failures back off up to one hour; malformed claims remain blocked for diagnosis. Concurrent flushes coalesce; disposal stops publication and timers/listeners are released. Retry uses the same server claim ID so a lost response cannot create another server claim.
- Queue entries bind to the earning UID. Another account cannot flush them. Requests carry an expected owner checked against server authentication; late responses cannot change a different account's active queue. Local item identity is checked before authority changes, and queue removal/item receipt update are atomic.
- Receipt listing now orders by document ID, returns up to 250 items with a continuation cursor, and includes authenticated owner identity. The client restores successive pages, rejects repeated cursors/wrong owners, and stops on account change. Restoring again retains the local stable claim and does not reward twice.
- This remains collected-item receipt restoration, not full Journal/character cross-device backup. The local Journal is still shared by the browser profile; account sign-out does not erase or partition it. Pending uploads are device-local and excluded from portable Journal backups to avoid implicit account transfer.

Validation: **1,628 registered component tests passed**, zero failed/skipped/TODO, plus source checks. Controlled endpoint tests verify 501 records over three pages, bad cursor rejection and expected-owner rejection. Real IndexedDB tests verify 501-item restore/retry/reload, pending-receipt reload/account switching/recovery, preservation through schema 3→4, and a bounded error when an older open connection blocks the upgrade. Existing two-tab save/backup/migration regression passed. Prescribed-client receipt and outbox fixtures passed with screenshots/state inspected and no error files. Actual source Quick Start desktop/phone and Space navigation regressions passed with zero page exceptions. Account and server responses were controlled fixtures; no authenticated service acceptance is claimed.

2. Complete cross-store reconciliation: interrupted Journal-to-backpack and companion reward flows, unavailable/quota-limited storage, corrupt/old backups and explicit rollback. Preserve original backups and stable reward identities.
3. Save-status presentation for queued, blocked, acknowledged and device-only records, using actual store state. Define explicit guest transfer and browser-local profile sharing behavior before offering full account continuity. Do not claim observations are cloud-backed through collected-item receipts.
4. Review legacy receipt restoration semantics (historical observation versus collection, evidence detail and stored authority) and account-switch races around already-started local transactions. The current local profile is not an account-isolated store.

Release requirements: deploy and verify compatible receipt Functions before promoting the new frontend; old responses without owner identity are intentionally not accepted as verified receipts. Schema 4 requires a rollback frontend that can open schema 4; do not roll back blindly to code that opens IndexedDB at version 3. No live browser data was upgraded in these tests; all browser writes used disposable test profiles. Production and backend remain unchanged.
