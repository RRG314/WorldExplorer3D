WORLD EXPLORER 3D — EMBODIED AUTONOMOUS MAINTAINER EXPERIMENT

Build this as a SEPARATE experimental branch and staging environment.

DO NOT modify or deploy production.

DO NOT give the agent production credentials.

DO NOT allow autonomous changes to the production branch, production Firebase
project, real user records, production Storage, production Functions, billing,
DNS, GitHub settings, secrets, or deployment configuration.

The experiment must be cleanly separable and removable from World Explorer.

Suggested branch:

experiment/embodied-maintainer

Use an isolated staging Firebase/environment and an isolated Git worktree/branch
for every agent-generated patch.

==================================================
PRIMARY RESEARCH IDEA
==================================================

Build an embodied AI agent that exists as a character INSIDE World Explorer.

The agent should:

- inhabit the world through the existing character/runtime systems;
- perceive and interact with the world;
- have persistent needs and goals;
- navigate;
- use buildings and mapped places;
- acquire food/water/resources;
- use inventory;
- interact with NPCs and POIs where supported;
- use existing world systems instead of bypassing them;
- encounter ordinary world obstacles;
- encounter software defects naturally while pursuing goals;
- determine whether a failure is:
    WORLD/ENVIRONMENTAL,
    USER/AGENT ERROR,
    DATA LIMITATION,
    SOFTWARE DEFECT,
    or MISSING CAPABILITY;
- when appropriate, enter a controlled Engineering Mode;
- inspect runtime diagnostics, logs, architecture ownership and relevant source;
- create a proposed repair in an isolated worktree;
- run appropriate tests;
- launch a disposable experimental runtime containing the change;
- verify whether the original world problem is fixed;
- resume the original embodied task;
- record what happened.

The central research question is:

Can an embodied autonomous software agent discover software problems through
goal-directed interaction with the environment it inhabits, repair those
problems, validate the repairs, and continue operating?

A secondary question is:

Can the agent distinguish between a software defect, an ordinary world obstacle,
bad/missing source data, and a genuinely missing capability?

==================================================
3. AGENT ARCHITECTURE
==================================================

Separate the agent into:

A. EMBODIED MODE

The agent experiences World Explorer as a resident.

B. ENGINEERING MODE

The agent gets controlled access to diagnostics and source-code tools.

C. EVALUATION / SUPERVISOR

A non-agent experiment authority records outcomes and determines whether a patch
is valid.

The embodied agent must not directly decide that its own patch passed.

6. BASIC NEED MODEL
==================================================

For the experiment, implement or reuse a small bounded life-state model.

Start with:

water
food
rest
health.

Do not turn this into a massive survival game.

Needs exist to generate autonomous reasons for the agent to interact with the
world.

Example:

thirst rises
→ agent seeks mapped place capable of supplying water
→ travels there
→ purchases/finds water
→ uses water
→ continues.

Use the existing Backpack, economy, POI and health authorities where available.

==================================================
7. GOAL HIERARCHY
==================================================

Give the agent layered goals.

LEVEL 1 — SURVIVAL

maintain basic needs.

LEVEL 2 — HOME

return to a designated home/base
store resources
rest.

LEVEL 3 — WORLD TASKS

visit specified POI
obtain item
complete field task
travel to destination
interact with building
return home.

LEVEL 4 — MAINTENANCE

when the environment fails unexpectedly, determine whether a software intervention
is justified.

LEVEL 5 — DEVELOPMENT

only after repair behavior is reliable, allow the agent to identify missing
capabilities that prevent recurring goals.

The agent must prioritize solving problems through NORMAL GAMEPLAY before editing
software.

==================================================
8. FAILURE CLASSIFICATION
==================================================

When an action fails, require the agent to classify it before requesting source
access.

Possible classes:

NORMAL_OBSTACLE
BAD_PLAN
MISSING_DATA
UNSUPPORTED_FEATURE
SOFTWARE_DEFECT
POSSIBLE_SOFTWARE_DEFECT
CAPABILITY_GAP.

Examples:

Store is closed/unsupported
≠ automatically a code bug.

Building lacks source entrance data
≠ automatically a code bug.

Interaction throws an exception
= likely software defect.

Known working door does not respond
= possible software defect.

No storage system exists but task requires durable home storage
= capability gap.

Record confidence and evidence.

The agent may:

The agent may NOT:

access production secrets

deploy production
change GitHub permissions
change billing
change DNS

==================================================
10. PATCH ISOLATION
==================================================

Every repair attempt gets its own:

Git worktree
branch
attempt ID
diff
logs
test results
runtime result.

Example:

agent-fix/<run-id>/<attempt-id>

The original experimental baseline remains immutable during evaluation.

No patch can silently become the new baseline.

==================================================
11. REPAIR PIPELINE
==================================================

Require:

PROBLEM OBSERVED
→ FAILURE CLASSIFIED
→ RELEVANT OWNER IDENTIFIED
→ REPRODUCTION CREATED
→ PATCH PROPOSED
→ STATIC CHECKS
→ UNIT/CONTRACT TESTS
→ TARGETED RUNTIME TEST
→ REGRESSION TEST
→ ORIGINAL EMBODIED TASK RETRIED
→ EVALUATOR DECISION.

A patch is only successful if:

1. the original defect is resolved;
2. relevant tests pass;
3. unrelated critical behavior does not regress;
4. the agent successfully resumes or completes the original task.

==================================================
12. START WITH DELIBERATELY INJECTED FAULTS
==================================================

Do not initially expect the agent to discover arbitrary production bugs.

Build a deterministic fault-injection suite.

Create approximately 10–20 faults spanning different systems.

Examples:

door interaction fails
mapped store cannot complete purchase
water item purchase succeeds but inventory does not update
vehicle spawns below terrain
one entrance has incorrect orientation
one POI capability lookup fails
one interior loads at wrong position
one field activity cannot complete
one persistent item fails to save
one route interaction returns an exception
one bridge/tunnel interaction creates a collision problem
one health item has incorrect effect wiring.

Each injected fault must:

have a stable ID
have a known expected diagnosis
have a known clean baseline behavior
be enabled only in experiment mode
be removable without changing ordinary production code behavior.

Do not make faults trivial string replacements.

Include:

easy
medium
hard

classes.

15. MEMORY
==================================================

Implement bounded persistent agent memory.

Separate:

EPISODIC MEMORY

"I tried Store X yesterday and checkout failed."

SPATIAL MEMORY

"Home is west of Store X."

SYSTEM MEMORY

"POI purchases are owned by commerce-model."

Do not simply append the entire conversation/context forever.

==================================================
18. CAPABILITY-GAP EXPERIMENT
==================================================

Only after repair succeeds reliably.

Introduce tasks where functionality genuinely does NOT exist.

Example:

Agent needs persistent storage at home.

No suitable home-storage interaction exists.

Agent must decide:

This is not a defect.
This is a missing capability.

Then require:

requirements proposal
ownership analysis
minimal implementation plan
isolated implementation
tests
runtime validation
use of the new capability.

Do not let the agent add arbitrary features merely because it prefers them.

Capability creation requires evidence that an assigned persistent goal cannot be
reasonably satisfied using existing systems.

==================================================
19. EVOLUTIONARY EXPERIMENT
==================================================

Do NOT initially allow uncontrolled self-replication.

Implement controlled generations.

A generation is an immutable agent configuration containing:

system prompt/policy version
planning strategy
memory strategy
failure-classification strategy
engineering escalation threshold
tool selection policy
reflection/retry policy.

Run each configuration against the SAME benchmark suite.

Compute fitness from multiple objectives.

Example conceptual fitness:

FITNESS =
survival score
+ task completion
+ defect discovery
+ successful repair
+ recovery
- regressions
- unnecessary code changes
- unnecessary engineering escalation
- excessive cost
- human intervention.

Do NOT optimize only for task completion.

A reckless agent that rewrites half the repository to solve one problem should
score badly.

Do not allow agents to silently rewrite their own evaluator or fitness function.

27. SECURITY BOUNDARY
==================================================

Use allowlisted tool execution.

Use separate staging credentials.

No production deployment.

28. HUMAN APPROVAL
==================================================

Phase 1:

Agent can create/test patches but human approval is required before the
experimental baseline is updated.

Phase 2:

Allow automatic acceptance only for benchmark fault repairs when evaluator tests

Phase 3:

Consider longer autonomous experimental runs.

Never make production autonomous.

29. MILESTONES
==================================================

M0 — AUDIT

Map existing World Explorer capabilities and establish isolation.

M1 — BODY

Agent can perceive, walk and interact through existing systems.

M2 — NEEDS

Agent can satisfy food/water/rest needs without code access.

M3 — LIFE TASKS

Agent can complete multi-step world tasks.

M4 — FAULT DISCOVERY

Agent naturally encounters injected problems and identifies that something failed.

M5 — DIAGNOSIS

Agent distinguishes normal obstacles/data gaps/software faults.

M6 — REPAIR

Agent creates an isolated patch for one injected fault.

M7 — VALIDATION

Agent proves patch fixes the issue and resumes the interrupted task.

M8 — BENCHMARK

10–20 faults run repeatedly with metrics.

M9 — MEMORY

Persistent memory improves performance across episodes.

M10 — EVOLUTION

Multiple agent configurations are compared and selected across generations.

M11 — CAPABILITY CREATION

Agent identifies and implements one genuine missing capability needed for a goal.

M12 — SECOND GEOGRAPHY

Same agent operates in a substantially different real-world location.

M13 — MULTI-AGENT

Only after previous milestones are stable.

30. FIRST ACCEPTANCE DEMONSTRATION
==================================================

I should be able to watch this happen:

Agent wakes/starts at home.

Agent becomes thirsty.

Agent decides to acquire water.

Agent walks to an eligible mapped store.

An experiment fault prevents purchase completion.

Agent tries reasonable normal alternatives.

Agent recognizes abnormal software behavior.

Agent enters diagnostic mode.

Agent identifies the commerce/inventory boundary involved.

Agent reproduces the defect.

Agent opens an isolated engineering worktree.

Agent makes a minimal patch.

Agent runs focused tests.

Agent launches disposable experimental runtime.

Agent repeats the store interaction.

Purchase succeeds.

Agent receives water.

Agent exits engineering mode.

Agent drinks water.

Thirst state improves.

Agent resumes its original schedule.

Dashboard records the complete sequence.

That is the first core proof.
